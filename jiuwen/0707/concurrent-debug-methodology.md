# 并发 Bug 调试方法论 — 通用可复用总结

从具体项目复盘中提炼，适用于任何并发/竞态条件 bug 的调试场景。

---

## 原则一：运行时观察优先于代码推理

**核心教训**：纯代码推理在并发 bug 中极易产生错误假设。并发行为只有运行时才能暴露。

**操作方法**：

1. **遇到并发 bug，第一步就是在关键路径添加诊断日志**
   - 覆盖：入口/出口、关键分支、状态变更点
   - 内容：线程名、会话/请求标识、关键状态值（不要只打 "here"，要打值）
   - **一次性添加所有诊断日志**，一次重启获取完整数据，避免多次重启逐点添加

2. **用日志数据验证/否定假设**
   - 每个假设必须在运行时数据中找到支持或否定证据
   - 没有否定前一假设前，不要跳到下一个假设

3. **诊断日志要区分"中间状态"和"最终结果"**
   - 轮询循环内部的中间状态（如 "还在等待"）不应与最终结果（如 "超时退出"）混为一谈
   - 只记录最终结果到 roundResult/businessResult 中，中间状态只在循环内部使用

**反模式**：
- 看代码 → 猜原因 → 改代码 → 测试 → 失败 → 再看代码 → 再猜 → 再改 → 再失败...
- 这是推理螺旋，每次重启只验证一个猜测，效率极低

---

## 原则二：聚焦共享状态，而非逐文件阅读

**核心教训**：并发 bug 的根因一定在"被多个线程/请求同时读写"的状态上。

**操作方法**：

1. **代码探索阶段直接搜索并发关键词**
   - 实例字段（非 thread-local）、`synchronized`、`volatile`、`ConcurrentHashMap`
   - 全局 Map/缓存（put/computeIfAbsent 等操作）
   - ID 生成逻辑（是否有请求间重复的可能）

2. **列出所有共享状态清单**
   - 对每个共享状态问：并发场景下，多个请求会读到同一个值吗？会写到同一个 key 吗？
   - 按风险排序，优先验证高风险状态

3. **ID/Key 生成是高频根因**
   - 并发请求中，任何基于"非请求级唯一"的 ID 都可能重复
   - 检查所有 ID 生成：taskId、sessionId、topicName、cacheKey
   - 确保 ID 包含请求级唯一标识（如请求序号、UUID）

**反模式**：
- 逐文件阅读整个模块，试图"全面理解"后再定位 bug
- 理解架构是必要的，但应快速聚焦到共享状态点

---

## 原则三：每次只改一处，改完立即验证

**核心教训**：一次改多处，无法区分哪个修复了问题，哪个是多余的。

**操作方法**：

1. **单一改动验证法**
   - 每次只改一处，改完立即构建+测试
   - 验证成功 → 确认该改动是根因修复
   - 验证失败 → 回退该改动，尝试下一个假设

2. **改动审查：逐一审视是否必需**
   - 根因修复 → 必需
   - 并发安全加固 → 必需（但要标注为加固而非根因）
   - "以防万一"的防御性改动 → 审慎考虑，可能引入新问题或非必需

3. **最终提交前，回退所有非必需改动**
   - 非必需改动增加代码审查负担和后续维护成本
   - 如果加固改动在根因修复后不再产生实际效果（如 topic 已唯一则 putIfAbsent 无意义），应回退

**反模式**：
- 一次改3处，测试成功后不知道哪个是关键修复
- 留下"以防万一"的改动，不审查是否在根因修复后仍然有意义

---

## 原则四：发现根因后，立即逆向追踪错误传播路径

**核心教训**：根因修复不等于用户体验修复。错误可能在传播链中被吞掉。

**操作方法**：

1. **从调用方视角逆向追踪**
   - 根因错误 → 中间处理层 → 最终响应
   - 确认每个环节是否正确传递了错误信息
   - 特别关注：catch 块是否静默消费了异常？result 是否被无条件标记为"成功"？

2. **检查 5 类常见错误吞没模式**
   - catch 块调用 resolveCompletion/setResult 但不传递到 stream/response
   - while 循环条件不检查 roundResult 是否包含错误（如无条件 markCompleted）
   - awaitCompletion/polling 逻辑把"非 timeout 错误"当作"完成信号"立即返回
   - 正常返回路径（不抛异常）导致 catch 块的错误写入逻辑不执行
   - 调用方只检查"是否完成"而不检查"是否成功"

3. **确保错误可见性**
   - 错误必须写入最终用户能看到的通道（stream、response、日志）
   - 如果错误只在内部状态中存在但不到达用户，这本身也是一个 bug

**反模式**：
- 修复了根因就认为任务完成
- 不追问"用户为什么只看到 completed 而不是错误信息"

---

## 原则五：优先利用项目已有运维工具

**核心教训**：手动分步操作（install → compile → start → wait）比一键脚本慢且易出错。

**操作方法**：

1. **开始工作前，先检查项目 bin/、scripts/、tools/ 目录**
   - restart.sh/py、start.sh/py、stop.sh/py、verify.sh/py
   - 这些脚本通常包含完整的构建→部署→验证流程

2. **一键脚本的优势**
   - 减少手动操作步骤（少犯错）
   - 包含等待就绪逻辑（避免手动猜启动时间）
   - 包含端口/进程管理（避免端口冲突）

3. **如果没有现成脚本，自己写一个并保留**
   - 核心动作：stop旧进程 → install → compile → start → wait-for-ready
   - 写好后保存到 bin/ 目录，后续复用

**反模式**：
- 每次手动执行 4-5 步构建流程
- 编译错误后才意识到参数格式问题（如 PowerShell 的 -D 参数）

## 原则六：假设管理 — 记录、追踪、不跳步

**核心教训**：多个假设交叉验证时，没有系统性追踪会导致重复验证和遗漏。

**操作方法**：

1. **显式记录每个假设**
   - 假设内容、预期现象、验证方法、验证结果
   - 用 TodoWrite 或笔记工具维护假设列表

2. **严格的状态流转**
   - 待验证 → 验证中 → 已否定（附证据） / 已确认（附证据）
   - 不跳步：否定假设 A 后才能开始验证假设 B

3. **假设来源分类**
   - 代码推理 → 低可信度，需要运行时验证
   - 运行时日志 → 高可信度，可直接定位
   - 用户反馈 → 中可信度，需要代码验证

**反模式**：
- 隐式假设（心里想但没记录）
- 跳步验证（假设 A 还没否定就开始验证假设 B）
- 重复验证（忘记之前已经验证过某个假设）

## 检查清单模板

遇到并发 bug 时，按以下顺序执行：

```
□ 1. 检查 bin/scripts/ 目录，找到一键构建/重启脚本
□ 2. 列出所有共享状态（实例字段、全局Map、ID生成逻辑）
□ 3. 一次性在关键路径添加诊断日志（入口/出口/状态变更/关键分支）
□ 4. 一键重启，运行并发测试，收集日志
□ 5. 从日志中定位根因（而非继续代码推理）
□ 6. 每次只改一处，改完立即验证
□ 7. 发现根因后，逆向追踪错误传播路径到最终用户
□ 8. 确保错误可见性（写入 stream/response）
□ 9. 审查所有改动，回退非必需改动
□ 10. 清理诊断日志和临时文件
```

## 效率度量

| 指标 | 本次实际 | 优化后目标 |
|------|----------|------------|
| 构建+重启次数 | 10 | 4-5 |
| 错误假设数量 | 2 | 0-1 |
| 诊断日志添加轮次 | 2 | 1 |
| 非必需改动数量 | 1（已回退） | 0 |
| 根因发现前的无效重启 | 6 | 1-2 |
| 总耗时比例（推理:观察:修复:审查） | 55:20:15:10 | 20:35:25:20 |
