## 4. 🟢 优化建议

### 4.1 立即可实施的优化

| # | 问题 | 优化方案 | 预期提升 |
|---|------|---------|---------|
| 1 | 首次响应延迟 6-39min | **先分析再读取**：先搜索文件概要/结构，确定需要修改的确切位置，再只读取必要部分 | 首次响应延迟降低50%+ |
| 2 | write_file超时 | **永远优先用patch**：对大文件修改一律用patch分段替换，不尝试write_file整体重写 | 消除超时事件，节省10+步骤 |
| 3 | patch导致文件损坏 | **修改后立即编译验证**：每修改完一个文件就编译一次，不要等全部改完再验证 | 及时发现错误，避免连锁损坏 |
| 4 | 缩进修改效率低 | **使用自动化工具**：用 `sed`/格式化工具处理批量缩进/空行，不要手动逐行patch | 1步 vs 15步 |
| 5 | Javadoc逐个补全 | **按文件批量修改**：读完一个文件后，列出所有需补全的位置，一次性生成完整修改 | 减少50%的patch调用 |
| 6 | 上下文膨胀4.4M | **减少重复读取**：读取文件后记住关键信息，不要反复重新读取同一文件 | 上下文减少30-40% |
| 7 | CodeArts重复分析 | **压缩后用memory保存关键发现**：在上下文压缩前，将关键发现写入memory或skill | 延续会话不重复50%+工作 |

### 4.2 流程级优化

#### A. 编码修改类任务的标准化流程

```
1. 读取修改计划文档 → 确定修改范围
2. 搜索模式确认位置 → search_files 确定需修改文件和行号（不读全部内容）
3. 按文件逐一处理：
   a. read_file 只读需修改的区域（用offset/limit）
   b. patch 精确修改
   c. terminal 编译验证（每文件改完就编译）
4. 更新计划文档状态
```

**预期效果**:
- 上下文减少 40-50%（不重复读取全文件）
- 工具调用减少 30-40%（批量而非逐个）
- 错误恢复更快（及时发现）

#### B. 逆向分析类任务的标准化流程

```
1. 先用 search_files/terminal 建立整体架构理解（不读2.5MB压缩文件）
2. 用 memory 记录关键发现（API、参数、调用链）
3. 对压缩代码使用 terminal+sed/awk 提取关键片段，不尝试整体理解
4. 建立CLI后，用 skill 保存操作步骤，供延续会话使用
```

**预期效果**:
- 首次响应延迟减少 60%+（不尝试理解2.5MB压缩文件）
- 上下文膨胀减少（不反复搜索同一内容）
- 延续会话可以直接从 memory/skill 继续

#### C. 通用优化原则

1. **小步快跑**: 每改完一个文件就编译验证，不要等全部改完
2. **分治策略**: 大任务拆成小子任务，每个子任务完成后保存进度到计划文档
3. **避免全文重写**: 优先使用 patch，永远不要用 write_file 重写整个文件（除非文件真的需要从头重写）
4. **缓存关键发现**: 用 memory 或 skill 保存跨会话需要的信息
5. **先读少后读多**: 先用 search_files 确定位置，再 read_file 读精确区域
6. **批量修改优先**: 同一文件的多个修改点，一次性生成所有 patch，不要逐个修改

### 4.3 技术配置优化

| 配置项 | 当前值 | 建议 | 原因 |
|--------|-------|------|------|
| max_iterations | 60-150 | 60（编码类）150（探索类） | 编码任务60足够，探索类需要更多 |
| reasoning_config | enabled=true | 编码类关闭，探索类开启 | 编码修改不需要深度推理 |
| 模型选择 | GLM-5.1 | 编码类用更快模型，探索类用强模型 | 减少首次响应延迟 |
