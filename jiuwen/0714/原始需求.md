详细描述
当前 deepagent 框架在超级智能体场景中采用单例模型创建实体，并指定统一的 tmp 临时目录作为工作空间。该实现方式在多租户企业客户场景下存在数据隔离不足的问题。

当前主要问题如下：
1、不同租户共享同一个实例工作空间及 tmp 临时目录，可能导致租户之间临时文件互相访问或写入干扰。
2、skill 目录当前对所有请求上下文可见，无法基于租户粒度隔离不同租户可访问的数据。
3、从智能体入口进入智能体后台后，系统当前只能感知不同 session，缺少基于租户 ID 的数据隔离能力。
4、在企业多租户场景下，该问题可能导致不同租户之间发生数据越界访问，不满足客户合规要求。

期望行为：
1、Deepagent 支持基于请求参数中的租户 ID 进行数据隔离。
2、租户粒度由业务方决定，可以是个人、部门或其他业务维度；agent 框架内不感知个人、部门等具体业务概念。
3、Agent 框架不负责租户合法性校验，也不判断用户是否属于某个租户。
4、Agent 框架仅根据请求参数中的租户 ID：

拉取该租户已有数据；
或在租户数据不存在时创建新的租户数据空间。
5、需隔离的数据包括：

租户维度的 skill 数据；
租户运行过程中临时生成的文件；
租户工作空间中的临时写入数据。
6、不需要隔离的数据包括：

智能体配置文件；
运行日志等公共运维类数据。
验收标准：
1、在测试中验证不同租户 ID 之间无法访问彼此的 skill 数据。
2、在测试中验证不同租户 ID 之间无法访问彼此临时生成的文件。
3、在测试中验证不同租户 ID 之间的临时写入不会互相影响。
4、当请求携带已有租户 ID 时，deepagent 能正确加载该租户对应的数据空间。
5、当请求携带新的租户 ID 且对应数据不存在时，deepagent 能创建新的租户数据空间。
6、验证不能通过路径拼接、相对路径、软链接等方式访问其他租户的数据目录。
7、验证 agent 框架不依赖个人、部门等业务字段即可完成租户数据隔离。

详细的环境信息描述
该问题属于框架级多租户数据隔离能力缺失，主要依赖 deepagent 当前超级智能体运行架构，与具体硬件环境无强绑定。

涉及环境包括但不限于：

场景：多企业客户 / 多租户使用场景
当前实现：单例模型创建实体，共享 tmp 临时目录作为工作空间
隔离标识：请求参数中的 tenant_id
租户含义：由业务方定义，可能是个人、部门或其他业务隔离粒度
框架职责：根据 tenant_id 拉取已有租户数据，或创建新的租户数据空间
非框架职责：不做租户合法性校验，不感知个人/部门等业务概念
隔离对象：租户 skill 数据、租户临时生成文件、租户工作空间临时写入数据
非隔离对象：智能体配置文件、运行日志等公共运维类数据

其他辅助信息
边界说明：
1、租户粒度说明：

deepagent 只识别 tenant_id；
tenant_id 代表个人、部门还是其他组织维度，由业务方决定；
agent 框架内部不引入个人、部门等业务概念。
2、租户校验说明：

agent 框架不负责租户校验；
agent 框架不判断请求方是否有权限访问某个 tenant_id；
租户 ID 的生成、传递和合法性校验由业务方保证。
3、存储基础设施说明：

租户数据暂时考虑挂载到分布式数据系统；
例如 GlusterFS、华为 SFS 或类似分布式文件存储；
4、相关基础设施由业务方提供；

deepagent 侧需要适配基于租户 ID 的数据目录组织和访问。
建议实现方向：
1、工作空间隔离：

按 tenant_id 创建独立 workspace / tmp 目录；
所有临时文件读写必须限制在当前 tenant_id 对应的隔离目录下；
文件访问需要做路径规范化校验，防止路径穿越；
同一 tenant_id 多次请求应复用该租户已有数据空间。
2、skill 数据隔离：

按 tenant_id 隔离 skill 数据目录；
不同 tenant_id 仅能看到自身隔离范围内的 skill；
skill 加载、查询、执行过程中均应基于当前请求的 tenant_id 定位数据。
3、租户数据初始化：

请求携带已有 tenant_id 时，加载该租户已有数据；
请求携带新的 tenant_id 且数据不存在时，创建该租户的数据空间；
创建过程需要具备并发安全性，避免多个请求同时初始化同一租户时产生冲突。
4、资源与存储管控：

需要考虑不同租户的临时文件存储上限；
需要考虑临时文件生命周期清理；
需要避免大量租户目录导致性能下降；
需要考虑分布式文件系统挂载异常、延迟、并发读写等场景下的稳定性。
