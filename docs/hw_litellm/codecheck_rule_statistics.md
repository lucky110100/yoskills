## 一、数据来源说明

数据中的 CodeCheck 问题来自 **LLM 调用日志里的工具返回内容**（`messages_json` 中 `role=tool` 的消息），而非原始 CodeCheck 平台导出文件。这些内容存在大量重复与格式变异，必须先做去重。

### 1.1 去重链路（四层）

| 层级 | 处理 | 数量 |
|------|------|------|
| 1 | 全部 JSON 文件中含规则 ID 的消息（未去重原始规模） | **24,097 条消息 / 225,154 次规则 ID 出现** |

> **关键**：方法论陷阱 7 的同类问题在此重演。同一份 CodeCheck 结果在后续每个请求快照中原样携带，导致同一条工具结果平均被 **47.3 个**快照文件记录（13,820 / 292）。若直接累加，规则 ID 出现 225,154 次，相对真实值 504 虚高 **446.7 倍**。

### 1.3 解析可靠性验证

用官方导出自带的声明做三重交叉校验（导出 `20261019204347`）：

| 校验项 | 官方声明 | 本次解析 | 结果 |
|--------|---------|---------|------|
| 导出总行数 | `Total rows: 360` | main 307 + test 53 = **360** | ✅ 完全一致 |

**G.OTH.03 差异解释（非错误）**：官方汇总把该规则拆成两行——
- `G.OTH.03 …--不用的import语句…: 5`
- `G.OTH.03 …--不用的代码段…: 1`

即同一规则 ID 下有 2 种不同规则名后缀。我的统计按规则 ID 汇总为 6 条，与「5 + 1」等价。**因此 355 与 360 的差 5 完全由该拆分导致，逐规则明细 100% 对齐。**

其余 20 条规则的数值（如 G.CMT.03 = 163、G.CMT.01 = 31、G.FMT.12 = 25、G.NAM.08 = 25、G.CMT.02 = 22）全部一一吻合。

**结论：解析器 1:1 命中，无漏读、无虚构。**

### 1.4 关于第二份导出 20261019231620

该份导出（同日晚 2.5 小时后重新导出）只有**部分文件被转述到日志中**：官方规则汇总声明共 131 条（16 条规则），但实际列出明细的仅 20 个文件、100 条（脚本按 `=== 文件名 (N issues) ===` 逐文件输出，日志被截断在若干个文件后）。

| 口径 | 定义 | 合计 | 适用场景 |
|------|------|------|---------|
| **A 归并漂移（推荐）** | 同 (文件, 规则, 描述) 取单份报告中出现的最大行号数 | **504** | 回答「实际有多少类问题点」 |
| **B 严格行号并集** | 同 (文件, 规则, 描述) 跨报告所有不同行号全部计入 | **588** | 回答「日志中出现过多少个问题位置」 |

**差异 84 条**全部来自行号漂移（同一问题点被移动后的旧行号）。下文主表按 **口径 A（504）** 展示，括号内为口径 B。

## 五、关键发现

### 5.1 注释类问题占绝对主导（55.56%）

`G.CMT.03`（Javadoc 需含功能说明及 @param/@return/@throws）单独占 **41.87%**，是第二名 G.CMT.01 的 6.4 倍。

**该规则按「每个缺失的标签」独立计数**，211 条拆解如下：

| 描述类型 | 条数 | 占该规则比例 |
|---------|-----:|-----:|
| `Parameter: xxx, Missing @param tag` | **100** | **47.4%** |
| `Missing @return tag` | 46 | 21.8% |
| `Javadoc content should appear in lines...`（格式问题） | 46 | 21.8% |
| `Missing function description` | 14 | 6.6% |
| `Exception: xxx, Missing @throws tag` | 5 | 2.4% |
| **合计** | **211** | 100%（五项已完整覆盖，无遗漏项） |

`Parameter:` 类共涉及 **50 个不同参数名**（handle 22 次、ns 15 次、payload 5 次……）——即一个方法有 5 个参数各缺一个 `@param`，就产生 5 条问题。

**因此数量大不等于缺陷严重**，不宜用总次数直接衡量代码质量水位；建议按「受影响的方法数」而非「标签缺失数」评估。

### 5.2 问题高度集中在 offload 模块

Top 10 文件占全部问题的 **46.0%**（232 / 504）：

| 文件 | 问题数 | 主要规则 |
|------|-----:|---------|
| OffloadConfig.java | 52 | CMT.03 / CMT.01 / NAM.08 |
| OffloadCatalog.java | 37 | CMT.03（35） |
| CompositeOffloadStore.java | 23 | CMT.03（19） |
| FileOffloadStore.java | 19 | CMT.03 / CON.10 |
| OffloadMessageBufferAdapter.java | 19 | CMT.03 / ERR.02 |
| OffloadJanitor.java | 19 | 并发 + 注释 |
| OffloadRequest.java | 18 | CMT.01 / CMT.03 |
| OffloadServiceImpl.java | 16 | ERR.02 为主 |
| SystemPromptBuilderConcurrencyTest.java | 15 | TYP.13 为主 |
| OffloadMarkerUtils.java | 14 | CMT.03（10） |

这说明 `core/context/offload` 子模块是 CodeCheck 门禁的主要阻力来源。

### 5.3 行号漂移揭示返工痕迹

同一问题在不同批次报告中的行号变化，可量化各规则的**返工强度**（口径 B − 口径 A）：

| 规则 | 漂移量 | 说明 |
|------|-----:|------|
| **G.ERR.02** | **+22** | 漂移最严重。如 OffloadJanitor.java 同一规则的行号从 L161 → L166 → L170 → L249 → L256 → L310 → L318，共 7 个位置，单份报告最多 3 个 |
| G.CMT.03 | +14 | 注释随代码增补而整体位移 |
| G.FMT.12 | +13 | 空行调整引起行号变动 |
| G.MET.06 | +11 | return null 改写反复 |

`G.ERR.02`（不要直接捕获 Exception/RuntimeException）漂移量居首，说明该问题被反复"挪位置"但始终未彻底清除，属于**技术债顽固点**，建议专项治理。

同时，`G.CMT.01/02`、`G.DCL.02`、`G.CON.08`、`G.EXP.03/04`、`G.FMT.04`、`G.MET.04/05`、`G.OBJ.04`、`G.TYP.04` 漂移量为 **0**，表示这些问题位置稳定、一次定位即可修复。

## 六、复现方式

脚本位于 `C:\Users\yaodonghai\WorkBuddy\common\output\codecheck\`：

| 脚本 | 作用 |
|------|------|
| `extract.py` | 扫描全部日志，按 `tool_call_id` 去重，解析 6 种格式（控制台表格 / 列表 / UI 快照 / 导出转储 / IDX 行 / 规则聚合），输出 `inst.pkl` |
| `final_stat.py` | 按问题身份去重、合并行号漂移与描述截断，输出 `result.json` |

运行顺序：`python extract.py && python final_stat.py`
