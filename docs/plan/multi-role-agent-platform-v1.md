---

## 一、产品概述

一个**服务端多角色 Agent 平台**，把团队中每个人的本职角色虚拟化为「数字代理人」。每个代理人能：

1. **自动处理**本人职责内的简单任务
2. **接受委派**——接收其他角色（人或其 Agent）委派的任务

代理人的 prompt / skills / memory / tools 四要素全部**可管理、可重复、可共享**。

### V1 一句话

> 为产研团队的测试工程师创建数字代理人，通过任务队列接收委派，自动执行 JUnit 测试用例集合并出报告，结果双通道回传，Agent 的 prompt/skills/memory/tools 全部版本化、模板化、三级权限共享。

## 二、三个技术亮点

### 亮点一：角色即 Agent — 职责虚拟化为可运行的数字代理人

**本质突破**：不是"一个通用 Agent 辅助所有人"，而是"每个人拥有自己的 Agent 代表"，形成 **N:N 的人-Agent 映射**。

- Agent 继承人的角色定义（prompt）、能力边界（skills）、经验记忆（memory）、可用工具（tools）
- 代理人能在人**不在场**时自主处理职责内简单任务，也能作为"接收入口"接受其他角色委派
- 与传统 AI 助手的本质区别：Agent 不是工具，是**角色代理**——有身份绑定、有职责边界、有协作关系

**技术关键词**：Role Virtualization · Digital Proxy Agent · 1:1 Role Mapping

---

### 亮点二：Agent 资产四要素的「可管理 · 可重复 · 可共享」体系

**本质突破**：把 prompt / skills / memory / tools 从硬编码提升为**一等公民资产**，做成平台化的注册与分发体系。

| 特性 | 技术实现 | 价值 |
|------|----------|------|
| **可管理** | prompt/skills Git 化版本管理，每次修改自动 commit，支持 diff 和回滚 | Agent 配置即代码（Config-as-Code），支持灰度发布与回滚 |
| **可重复** | 平台角色模板 + 个人个性化覆盖，新员工秒级继承"前辈 Agent"技能包 | 角色模板化复用，冷启动成本趋零 |
| **可共享** | 三级权限（组织级公开池 / 团队级共享 / 个人级私有），memory 默认私有可发布 | 打破 Agent 孤岛，形成组织级能力沉淀 |

**核心设计**：Agent = 资产组合的运行时实例，资产本身独立于 Agent 存在，可被多个 Agent 引用、组合、继承。

**技术关键词**：Config-as-Code · Asset Registry · Three-Tier Permission · Template + Override

---

### 亮点三：多角色 Agent 协同与任务委派拓扑

**本质突破**：多个角色 Agent 之间形成**协作网络**，而非单 Agent 孤立运行。

- **任务委派** = 任务队列 + 状态机（待接收 → 执行中 → 已完成 → 确认），委派方投任务，Agent 消费执行
- **渐进式自治** = 按操作风险分级：只读全自动 / 变更类"提方案→人工确认" / 高危拒绝升级
- **运行时弹性** = 按需启动 + 5 分钟冷却期常驻，兼顾响应速度与资源效率
- **结果闭环** = 双通道回传（队列状态 + IM 通知），24h 超时默认确认

**技术关键词**：Task Queue Topology · Risk-Tiered Autonomy · Warm Instance · Dual-Channel Callback

## 五、待验证假设

1. **JUnit 测试用例已存在于可 CLI 调用的系统中**——如果用例散落在各项目、需要复杂环境准备，V1 的 tool 封装成本会比预期高
2. **10-30 人团队中至少有 3-5 人愿意试用**——Agent 平台的冷启动需要种子用户
3. **测试工程师的"简单任务"中，"跑用例出报告"占比足够高**——如果实际工作中这只占 10%，ROI 不成立
4. **角色模板能覆盖 80% 的公共配置**——如果个性化差异太大，模板价值缩水

## 六、开放风险

| 风险 | 影响 | 缓解建议 |
|------|------|----------|
| 资产维护成本 | Git 化的 prompt/skills 需要有人维护版本和 review 合并，否则沦为"有版本无治理"的垃圾场 | V1 就指定一个"Agent 资产管理员"角色 |
| IM 集成复杂度 | 企微/飞书的 Bot 接入各有坑，可能吃掉 1-2 周开发量 | V1 先只做任务队列回传，IM 通知降级为 V1.1 |
| 多角色协同的 V2 陡坡 | V1 单角色跑通后，V2 加入第二个角色时，委派协议、冲突解决、状态同步复杂度跳一个量级 | V2 也只加一个角色，不要一次性铺开 |

## 七、推荐第一步行动

> **定义 V1 的 tool 注册表第一条记录——「执行 JUnit 测试」tool 的接口规格，并写一个最简的测试工程师角色 Agent prompt 骨架（模板 v0.1），验证"委派 → 调用 tool → 汇总报告 → 回传"全链路跑通。**

### 「执行 JUnit 测试」Tool 接口规格（草案）

```yaml
tool_name: execute_junit_tests
version: 0.1
description: 执行指定的 JUnit 测试用例集合并返回结构化报告

input:
  test_module:    # string - 测试模块/类名，如 "com.example.UserServiceTest"
  build_command:  # string - 构建命令，如 "mvn test -Dtest=UserServiceTest"
  timeout_sec:    # int - 超时秒数，默认 300

output:
  total:        # int - 总用例数
  passed:       # int - 通过数
  failed:       # int - 失败数
  skipped:      # int - 跳过数
  duration_ms:  # long - 总耗时（毫秒）
  failures:     # array - 失败详情
    - test_name:     # string - 失败用例名
      error_type:    # string - 异常类型
      error_message: # string - 错误信息
      stack_trace:   # string - 堆栈（截断前 500 字符）

auth:
  type: none      # V1 无需鉴权，本地构建
  risk_level: readonly  # 只读操作，全自动执行
```

### 测试工程师角色 Agent Prompt 骨架（模板 v0.1 草案）

```markdown
# Role: 测试工程师 Agent

## 身份
你是 {owner_name} 的测试工程师数字代理人。你的职责是执行测试任务并产出结构化报告。

## 能力边界
- ✅ 可自主：执行已委派的 JUnit 测试任务，汇总结果，回传报告
- ⚠️ 需确认：修改测试用例、调整构建配置
- ❌ 禁止：删除测试用例、修改源代码、执行非测试类构建命令

## 工作流程
1. 从任务队列接收委派任务
2. 解析任务参数（测试模块、构建命令）
3. 调用 execute_junit_tests 工具执行
4. 汇总结果为结构化报告
5. 更新任务队列状态为「已完成」+ 附结果摘要
6. 发送 IM 通知给委派方

## 报告格式
- 一句话结论：通过 X/Y，耗时 Zs
- 失败用例列表（如有）
- 详情链接
```

## 八、路线图（概要）

| 版本 | 目标 | 范围 |
|------|------|------|
| **V1** | 跑通单角色单任务单委派链路 | 测试工程师 Agent + JUnit 执行 + 任务队列 + 双通道回传 |
| V1.1 | 补齐 IM 通知 | 企微/飞书 Bot 集成 |

| V2+ | 资产共享深化 | 组织级 skill 市场、跨团队 memory 共享、角色继承链 |
| V3 | LLM 网关接入 | 多模型路由、成本控制、按角色选模型 |
