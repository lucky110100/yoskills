# Feature Analysis — 工程特性功能分析技能

> 本技能用一套系统化方法论分析工程的功能特性，目标是「理解 → 定位 → 追踪 → 建模 → 验证 → 固化」，减少重复工作并支持团队共享演进。与 `code-wiki-author` 互补：本技能偏「分析与索引」(理解的产物)，`code-wiki-author` 偏「文档化」(成文的产物)；先分析后文档化，二者可串联。

---

## 一、何时调用

- 接手/维护一个陌生工程，需要快速建立全局认知
- 重构/优化前，要先理清耦合点与瓶颈
- 排查 bug，需要定位相关调用链与边界
- 在既有工程上扩展新功能，要先摸清扩展点和约定
- 建立可演进的「特性索引」作为团队共享基线
- 用户要求「分析这个项目/这个功能怎么实现的/梳理特性清单」

**不适用：** 单文件/小脚本理解(直接 Read 即可)、纯文档生成(走 `code-wiki-author`)、纯 bug 修复(走 `efficient-task-flow` 错误驱动路径)。

---

## 二、核心方法论（多策略可切换）

### 2.1 C4 模型分层（由粗到细）
Context（系统边界）→ Container（进程/服务）→ Component（模块/包）→ Code（类/函数）。
分析功能时先确定它在哪层，只往下一层挖，避免一上来陷进代码细节。

### 2.2 4+1 视图（多视角切分）
逻辑视图 / 进程视图 / 开发视图 / 物理视图 / 场景视图。
对每个功能问「它在 5 视图里各是什么形态」，避免遗漏跨层影响。

### 2.3 特性定位三路线（必须并查，单一手段常漏）
- **静态法**：Grep / 符号依赖（精确术语）
- **动态法**：跑一遍功能，抓执行轨迹/调用栈（行为不明时）
- **文本法**：SearchCodebase 语义检索（描述模糊时）
- **混合法最优**：文本定位种子 → 静态扩展 → 动态验证

### 2.4 影响分析（可追踪性矩阵）
正向：改了这个会动哪些（trace forward）；逆向：谁会调用到这个（trace backward）。
建立「特性 ↔ 代码 ↔ 测试」可追踪性矩阵，这是特性索引的核心结构。

### 2.5 代码理解三模式
Top-down（领域→代码）/ Bottom-up（语句→概念）/ Opportunistic（按线索随时切换）。
高手常态是机会型，不要固执单一方向。

### 2.6 ADR（架构决策记录）
为每个关键特性附一条 ADR：背景、决策、后果、替代方案。让索引不只记「在哪」，还记「为什么」。

## 三、工具清单

### 3.1 TRAE 内置
| 工具 | 何时用 |
|------|--------|
| SearchCodebase | 语义/模糊定位（文本法特性定位，跨文件一次获取上下文） |
| Grep | 精确术语、正则、按文件类型过滤（静态法） |
| Glob | 按命名约定批量定位文件 |
| LS | 摸目录骨架 |
| Read + offset/limit | 抽样读大文件关键段（>500行必须先定位再精读） |
| Task（子代理） | 并行广度探索，回传聚合结论，省主上下文 |
| RunCommand | 跑 build/lint/typecheck/test/git log |
| WebSearch/WebFetch | 查陌生库/框架文档 |
| skill-creator | 把本方法或子流程再封装成更多 Skill |
| Schedule | 定期重跑特性索引校验，发现漂移 |

### 3.2 可外挂（若环境已装，用 RunCommand 调用）
- **ast-grep**：按 AST 结构搜代码，比 grep 精准
- **semgrep**：自定义规则做模式扫描（如「找所有未捕获的 Promise」）
- **madge / dependency-cruiser**（JS）：依赖图，找循环/孤立模块
- **ArchUnit**（Java）：用测试断言架构规则（如「Service 不能调 Controller」）
- **radon/lizard/gocyclo**：复杂度热点，定位高危函数
- **universal-ctags/global**：符号索引与反向查找
- **git log/blame**：历史驱动，看功能怎么演化来的

> 建议在分析前先用 `RunCommand` 探一下环境装了哪些(`ast-grep --version`、`semgrep --version` 等)。

## 四、决策树

### 决策树 A：选主策略（按已知程度）
```
你对该功能知道什么？
├─ 只知道功能名/模糊描述 → 语义检索(SearchCodebase) → 看命中数
│   ├─ 命中少(<10) → 直接 Read 全文
│   └─ 命中多 → 加限定词 / Grep 按类型收窄 → 回到本树
├─ 知道具体术语/关键词 → Grep 精确匹配
├─ 知道大概文件/路径 → Glob + Read
├─ 知道「做什么」但不知代码 → 读测试反推契约
└─ 只想摸整体架构 → LS + Glob + 读入口 + C4 分层
```

### 决策树 B：选验证手段（按可运行性）
```
能否运行工程？
├─ 能跑 → 有测试套件？
│   ├─ 有 → 跑相关测试 + 复杂度热点双查
│   └─ 无 → 写探针测试 / 加日志观察行为
├─ 只能静态看 → 三路交叉印证（文本+静态+历史）
└─ 不确定 → 先跑 build/typecheck 探活
```

### 决策树 C：何时升级到子代理（按上下文与并发度）
```
分析规模评估
├─ 单链路、范围小 → 主会话直接做
├─ 多模块且相互独立 → 并发子代理，各回传聚合结论
├─ 单链路但极深 → 串行子代理接力，避免主上下文爆
└─ 主上下文已 >70% → 立即派子代理承接广度搜索
```

### 决策树 D：选固化产物（按复用范围）
```
这套方法/知识给谁用？
├─ 跨项目、跨会话都想要 → 自定义 Skill（skill-creator）
├─ 仅本项目 → .trae/rules/project_rules.md + 项目内 docs
├─ 团队人工查阅 → ADR + 特性索引文档
└─ 一次性 → 不固化
```

## 五、执行流水线（标准 7 步）

1. **工程位置确认** → `LS` + 读 `package.json`/`README`/`pom.xml`/`go.mod` 等 → 建 C4-Context 骨架
2. **通览发现特性** → 并发子代理分模块探索（决策树 C），各回传「特性候选清单」
3. **三路特性定位** → 静态(Grep/ast-grep) + 文本(SearchCodebase) + 动态(跑测试/执行轨迹)（决策树 A、B）
4. **建特性索引** → 特性 ↔ 代码 ↔ 测试 可追踪性矩阵 + 每特性附 ADR
5. **交叉验证** → build + typecheck + lint + 针对性测试全跑一遍
6. **固化** → 项目约定写 `.trae/rules/project_rules.md`；把本流水线用 `skill-creator` 封装成 Skill
7. **演进** → 用 `Schedule` 定期重跑特性索引校验，发现漂移即更新

## 六、策略调整信号（遇到就切策略）

| 信号 | 调整 |
|------|------|
| 搜索结果太多 | 收窄：加限定词、glob 限类型、看上下文筛选、改用语义检索 |
| 搜索结果为空 | 放宽：试同义词、换命名习惯(驼峰/下划线)、查缩写/别名 |
| 读一个文件太久 | 抽样：先 Grep 看骨架(函数签名/类定义)，再定点 Read 关键行段(offset+limit) |
| 主上下文快满 | 派子代理(Task)做广度探索，只回传聚合结论 |
| 并行任务独立 | 批处理：一条消息发多个工具调用并发执行 |
| 理解与测试/运行矛盾 | 推翻重建：接受代码事实，重读关键路径，更新心智模型，不迁就假设 |
| 任务复杂步骤多 | 用 TodoWrite 拆解，逐个完成逐个打勾 |

### 反模式（必须避免）
```
❌ 一上来全文 Read 大文件(应先 SearchCodebase/Grep 定位)
❌ 只用单一手段定位特性(静态/动态/文本必须并查)
❌ 主上下文已满还硬撑不派子代理(导致后续失忆)
❌ 理解与测试矛盾却坚持假设、强行解释代码
❌ 分析完不固化，下次同类工程又从零摸(重复工作)
❌ 不建特性索引，团队各自重复摸底(无共享基线)
```

## 七、效率判定（给技能本身打分）

效率分 = 覆盖率×0.3 + 质量分×0.4 + 成本分×0.2 + 速度分×0.1
- 覆盖率 = 自主完成步骤数 / 任务总步骤数
- 质量分 = 1 − 失败率（通过验证的产出比例）
- 成本分 = 基准 token / 实际 token（越省越高）
- 速度分 = 基准耗时 / 实际耗时（越快越高）

**对照基准**：和「不用本技能、纯手动」做同一任务对比，省了多少 token / 多少轮 / 多少时间才算有效。

| 维度 | 含义 | 信号 |
|------|------|------|
| 触发准确性 | 该用时用、不该用不乱用 | description 匹配任务才触发 |
| 任务覆盖率 | 自主完成比例 | 80% 自动 vs 20% 就需接管 |
| 输出质量 | 正确/完整/可用 | 一次成功 vs 反复修正 |
| 资源成本 | token 与工具调用数 | 几次调用完成 vs 转几十轮 |
| 错误率/重试率 | 失败与纠偏频率 | 0 次重试 vs 平均 3 次 |

## 八、输出约定

- **特性索引**：存为 `docs/feature-index.md`（或团队约定路径），结构表格：
  `| 特性名 | 职责 | 代码位置 | 测试位置 | 依赖 | ADR 链接 |`
  代码位置用 `[basename](file:///绝对路径#L行号)` 可点击直达
- **项目规则**：写 `.trae/rules/project_rules.md`，含 lint/typecheck/test 命令、命名约定、分层约定
- **ADR**：关键特性附 ADR，存 `docs/adr/NNNN-title.md`，字段：背景/决策/状态/后果/替代方案
- **特性索引演进**：每次新增/改动特性，在索引表追加或更新一行，并记一条更新记录

---

## 九、执行规则（强制）

1. **意图不清不动手**：复杂分析前用 AskUserQuestion 提选择/是否题(禁止自由作答)，批量提问(每次最多 4 个)
2. **语言一致**：输出语言与用户最新消息语言一致
3. **不擅自提交**：不主动 git commit，除非用户明确要求
4. **不擅自创建**：优先编辑现有文件，不创建非必要文件，不主动建 README/文档除非要求
5. **任务追踪**：多步骤任务用 TodoWrite 实时追踪，完成即标记
6. **验证后宣称**：完成前用 grep/ls/build/test 验证结构与理解，证据先于断言
7. **三路并查**：特性定位必须静态+动态+文本三路交叉印证，不靠单一手段
8. **固化优先**：分析成果按决策树 D 固化，避免下次重复摸底

## 十一、适用与边界

**适用：**
- 中大型代码仓库(>5 子模块，>5000 行)的功能特性梳理
- 接手陌生工程前的快速摸底
- 重构/加新功能前的扩展点与约定梳理
- 建立团队共享、可演进的特性索引基线

**不适用：**
- 单文件/小脚本(直接 Read 即可)
- 纯文档生成(走 `code-wiki-author`)
- 纯 bug 修复(走 `efficient-task-flow` 错误驱动路径)
- 一次性 README(通用写作即可)

**串联建议：**
`feature-analysis`(理解+索引) → `code-wiki-author`(成文档) → `efficient-task-flow`(改代码) 形成完整闭环。
