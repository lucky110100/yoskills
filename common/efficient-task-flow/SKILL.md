# Efficient Task Flow — AI任务高效执行策略

本Skill定义了一套经过数据分析验证的AI任务执行优化流程，核心目标是**减少搜索步骤、降低返工率、加速任务完成**。

基于TRAE CN近2天147,933行日志的分析，识别出搜索:修改比率5.2:1、同文件返工10+次、沙箱100%崩溃等关键问题后，提炼出以下5种优化策略。

---

## 核心原则

1. **先理解再动手** — 用SearchCodebase一次性获取完整上下文，而非逐步Read+Grep拼凑
2. **先规划再执行** — 用TodoWrite列出所有修改点，避免遗漏导致返工
3. **先验证再结束** — 用RunCommand编译/测试验证，确保修改正确
4. **批量优于逐次** — 多个相关修改在同一步骤完成，而非逐文件反复修改
5. **缓存优于重复** — 对话内搜索结果应被记住，避免重复搜索同一代码

---

## 策略一：预搜索 → 批量修改

### 何时使用
任何涉及代码修改、重构、调试的任务，尤其是需要修改多个文件时。

### 执行流程

```
Step 1: SearchCodebase — 用自然语言描述意图，一次性获取跨文件的语义相关代码
Step 2: TodoWrite — 规划所有需要修改的文件和位置，列出修改顺序
Step 3: Read — 仅读取确认需要修改的目标文件(而非所有可能相关的文件)
Step 4: SearchReplace — 按规划批量修改，尽量在同一步骤完成所有修改
Step 5: RunCommand — 编译/测试验证结果
Step 6: 如验证失败，在当前步骤内修正，而非开启新一轮修改循环
```

### 搜索工具优先级

```
优先级1: SearchCodebase — 语义搜索(首选，一次获取跨文件上下文)
优先级2: Grep — 精确搜索(辅助，定位特定模式如类名/方法名)
优先级3: Read — 只在确认需要修改时才读取文件内容
优先级4: Glob — 只在需要发现文件位置时使用
```

### 反模式(必须避免)

```
❌ Read文件 → 修改 → 发现问题 → Read同一文件 → 再修改 → Read另一文件 → 修改... (循环返工)
❌ Grep搜索关键词 → 逐个Read搜索结果 → 逐个修改 (搜索碎片化)
❌ 不规划直接修改，遗漏修改点后反复补充 (返工)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 搜索:修改比率 | 5.2:1 | 2:1 |
| 同文件返工次数 | 5-10次 | 2-3次 |
| SearchCodebase占比 | 1.7% | 30%+ |
| Read占比 | 31.7% | <15% |

## 策略二：错误早发现

### 何时使用
修改代码后，尤其是Java项目修改后、配置文件修改后、脚本修改后。

### 执行流程

```
Step 1: 修改前 — RunCommand检查当前状态
  - Java项目: mvn compile (确认编译通过)
  - Python项目: python -m py_compile <file> (确认语法正确)
  - 通用: git status (确认工作区状态)

Step 2: 执行修改 — SearchReplace批量修改

Step 3: 修改后立即验证 — RunCommand
  - Java项目: mvn compile && mvn test
  - Python项目: pytest 或 python <file>
  - 通用: 项目的lint/typecheck命令

Step 4: 验证失败时 — 在当前步骤内分析错误、修正代码
  - 不要回到Step 1重新搜索
  - 直接针对错误信息修正
  - 修正后再验证

Step 5: 验证通过 — 标记任务完成
```

### 反模式(必须避免)

```
❌ 修改完成后不验证，等用户反馈才发现错误
❌ 验证失败后开启全新的搜索+修改循环(而非在当前步骤内修正)
❌ 修改了A文件但忘记验证B文件(依赖文件)的编译状态
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| undo操作 | 5次/2天 | 0-1次/2天 |
| 返工率 | 60% | <20% |

## 策略三：搜索结果缓存

### 何时使用
多步骤任务中需要多次搜索同一代码区域时。

### 执行流程

```
Step 1: 第一次搜索 — 正常执行SearchCodebase/Grep/Read
Step 2: 在TodoWrite或回复中记录已搜索的关键发现
  - 记录: 哪些文件已读取、哪些代码位置已确认
  - 后续步骤可以复用这些发现

Step 3: 后续步骤 — 优先复用已获取的上下文
  - 如果已读取文件A的内容，不再重复Read文件A
  - 如果已SearchCodebase获取某模块的上下文，不再重复搜索
  - 除非文件被修改(由SearchReplace导致)，才需要重新Read

Step 4: 文件修改后 — 只重新读取被修改的文件
  - 用SearchReplace修改文件后，如果需要再次引用该文件内容
  - 才执行Read重新获取修改后的版本
```

### 反模式(必须避免)

```
❌ 在同一对话中多次Read同一文件(文件内容未变化时)
❌ 在同一对话中多次SearchCodebase同一查询
❌ 搜索得到结果后不记录，后续步骤又重新搜索同一内容
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 重复搜索率 | ~30% | <10% |
| 平均工具调用数/任务 | 10次 | 5次 |

## 策略四：分层规划

### 何时使用
复杂任务(涉及3+文件修改、架构调整、新功能开发)开始前。

### 执行流程

```
Step 1: 理解层 — SearchCodebase获取代码架构和关键路径
  - 搜索项目整体结构
  - 搜索目标模块的依赖关系
  - 搜索相关的设计文档或README

Step 2: 规划层 — TodoWrite列出所有修改点
  - 列出每个需要修改的文件
  - 列出每个文件中的修改位置
  - 列出修改的顺序(考虑依赖关系)
  - 列出验证步骤

Step 3: 执行层 — 按规划顺序执行SearchReplace
  - 按TodoWrite的顺序逐个修改
  - 尽量把同一文件的多个修改合并为一次SearchReplace
  - 修改后标记TodoWrite对应项为completed

Step 4: 验证层 — RunCommand编译+测试
  - 执行编译确认所有修改无语法错误
  - 执行测试确认功能正确
  - 如有错误，在当前步骤内修正

Step 5: 修正层 — 仅在验证失败时进入
  - 分析错误信息
  - 针对错误精确修正(而非重新搜索)
  - 修正后再次验证
```

### 反模式(必须避免)

```
❌ 不规划直接开始修改(导致遗漏、返工)
❌ 修改了文件A后才发现还需要修改文件B(依赖发现不及时)
❌ 逐文件单独修改而非批量规划(同模块文件应一起修改)
```

### Java项目专用规划模板

```
TodoWrite规划模板:
1. [理解] SearchCodebase获取<模块>完整上下文
2. [理解] 确认所有需要修改的文件列表
3. [修改] <文件1>: <修改描述>
4. [修改] <文件2>: <修改描述>
5. [修改] <文件3>: <修改描述>
6. [验证] mvn compile 确认编译通过
7. [验证] mvn test -Dtest=<TestClass> 确认测试通过
```

## 策略五：智能工具选择

### 何时使用
每个搜索步骤开始时，选择最合适的搜索工具。

### 工具选择决策树

```
需要搜索代码 → 问题类型?
  ├─ "这段代码的作用是什么?" → SearchCodebase (语义理解)
  ├─ "哪里使用了XXX类/方法?" → SearchCodebase (依赖追踪)
  ├─ "XXX模式在哪些文件中出现?" → Grep (精确模式匹配)
  ├─ "项目中有哪些XXX类型的文件?" → Glob (文件发现)
  ├─ "我需要修改这个文件" → Read (仅在确认修改目标后)
  ├─ "这个错误是什么原因?" → SearchCodebase + Grep (先语义再精确)
  └─ "这个模块的整体设计?" → SearchCodebase (架构级理解)
```

### 工具效率对比

| 工具 | 上下文获取量 | 调用成本 | 适用场景 |
|------|-------------|----------|----------|
| SearchCodebase | 高(跨文件语义片段) | 1次调用 | 理解意图、架构、依赖 |
| Grep | 中(精确匹配行) | 1次调用 | 定位特定类名/方法名/字符串 |
| Read | 高(完整文件) | 1次调用 | 仅在确认修改目标后 |
| Glob | 低(文件路径列表) | 1次调用 | 发现文件位置 |
| LS | 低(目录结构) | 1次调用 | 了解项目目录结构 |

### 反模式(必须避免)

```
❌ 用Read逐文件读取来理解项目(应先用SearchCodebase)
❌ 用Grep逐关键词搜索来拼凑上下文(应先用SearchCodebase获取语义上下文)
❌ 在不确定修改目标前就Read文件(浪费上下文窗口)
❌ 搜索到结果后不分析直接修改(应先理解再修改)
```

## 系统性问题修复建议

以下问题不是Skill能解决的，但执行任务时应注意规避：

### 沙箱崩溃(Sandbox Crash)

- 现象: RunCommand可能因沙箱崩溃而丢失结果
- 规避: 如果RunCommand返回异常(空结果/错误)，等待2-3秒后重新执行
- 根因修复: 需要升级TRAE CN的sbox SDK版本或修复路径配置

### Job持久化失败

- 现象: Task子Agent状态可能丢失
- 规避: 避免依赖Task工具的长时运行结果，尽量在主对话中完成所有步骤
- 根因修复: 需要修复8.3短路径名问题(YAODON~1 → yaodonghai)

### LLM响应延迟

- 现象: 首Token最大可达14.6秒
- 规避: 简单任务(单文件修改/代码解释)建议使用Doubao-Seed-Code快速模型
- 复杂任务(多文件重构/架构设计)使用GLM-5.1或更强模型

## 执行清单(每次任务开始前检查)

```
□ 1. 是否先用SearchCodebase获取完整上下文? (而非逐文件Read)
□ 2. 是否用TodoWrite规划了所有修改点? (而非直接动手)
□ 3. 是否按优先级选择了搜索工具? (SearchCodebase > Grep > Read > Glob)
□ 4. 是否规划了验证步骤? (RunCommand编译/测试)
□ 5. 是否避免重复搜索已获取的上下文? (缓存搜索结果)
□ 6. 是否批量修改而非逐次修改? (同模块文件一起修改)
□ 7. 是否在验证失败时在当前步骤内修正? (而非开启新循环)
```
