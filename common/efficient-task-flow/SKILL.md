# Efficient Task Flow — AI任务高效执行策略

本Skill定义了一套经过数据分析验证的AI任务执行优化流程，核心目标是**减少搜索步骤、降低返工率、加速任务完成**。

基于TRAE CN近2天147,933行日志的分析，识别出搜索:修改比率5.2:1、同文件返工10+次、沙箱100%崩溃等关键问题后，提炼出以下9种优化策略。

---

## 核心原则

1. **先理解再动手** — 用SearchCodebase一次性获取完整上下文，而非逐步Read+Grep拼凑
2. **先规划再执行** — 用TodoWrite列出所有修改点，避免遗漏导致返工
3. **先验证再结束** — 用RunCommand编译/测试验证，确保修改正确
4. **批量优于逐次** — 多个相关修改在同一步骤完成，而非逐文件反复修改
5. **缓存优于重复** — 对话内搜索结果应被记住，避免重复搜索同一代码
6. **类型决定路径** — 不同任务类型有不同的最优执行路径，先分类再行动

---

## 策略一：预搜索 → 批量修改

### 何时使用
任何涉及代码修改、重构、调试的任务，尤其是需要修改多个文件时。

### 执行流程

```
Step 1: SearchCodebase — 用自然语言描述意图，一次性获取跨文件的语义相关代码
Step 2: TodoWrite — 规划所有需要修改的文件和位置，列出修改顺序
Step 3: Read — 仅读取确认需要修改的目标文件(而非所有可能相关的文件)
Step 4: SearchReplace — 按规划批量修改，尽量在同一步骤完成所有修改
Step 5: RunCommand — 编译/测试验证结果
Step 6: 如验证失败，在当前步骤内修正，而非开启新一轮修改循环
```

### 搜索工具优先级

```
优先级1: SearchCodebase — 语义搜索(首选，一次获取跨文件上下文)
优先级2: Grep — 精确搜索(辅助，定位特定模式如类名/方法名)
优先级3: Read — 只在确认需要修改时才读取文件内容
优先级4: Glob — 只在需要发现文件位置时使用
```

### 反模式(必须避免)

```
❌ Read文件 → 修改 → 发现问题 → Read同一文件 → 再修改 → Read另一文件 → 修改... (循环返工)
❌ Grep搜索关键词 → 逐个Read搜索结果 → 逐个修改 (搜索碎片化)
❌ 不规划直接修改，遗漏修改点后反复补充 (返工)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 搜索:修改比率 | 5.2:1 | 2:1 |
| 同文件返工次数 | 5-10次 | 2-3次 |
| SearchCodebase占比 | 1.7% | 30%+ |
| Read占比 | 31.7% | <15% |

## 策略二：错误早发现

### 何时使用
修改代码后，尤其是Java项目修改后、配置文件修改后、脚本修改后。

### 执行流程

```
Step 1: 修改前 — RunCommand检查当前状态
  - Java项目: mvn compile (确认编译通过)
  - Python项目: python -m py_compile <file> (确认语法正确)
  - 通用: git status (确认工作区状态)

Step 2: 执行修改 — SearchReplace批量修改

Step 3: 修改后立即验证 — RunCommand
  - Java项目: mvn compile && mvn test
  - Python项目: pytest 或 python <file>
  - 通用: 项目的lint/typecheck命令

Step 4: 验证失败时 — 在当前步骤内分析错误、修正代码
  - 不要回到Step 1重新搜索
  - 直接针对错误信息修正
  - 修正后再验证

Step 5: 验证通过 — 标记任务完成
```

### 验证粒度自适应

验证成本应与修改风险成正比，不要对所有修改都用相同的验证级别：

```
修改类型 → 验证级别
  ├─ 单参数/字符串变更 → 仅运行目标测试 (跳过compile)
  ├─ 单方法/逻辑修改 → compile + 目标测试
  ├─ 多文件修改 → compile + 目标测试 + 依赖模块测试
  ├─ 重构/接口变更 → compile + 全量测试套件
  └─ 配置文件修改 → 检查配置加载 + 相关功能测试

原则:
  - 低风险修改用轻量验证，高风险修改用重量验证
  - 单行参数变更不需要完整compile，直接运行测试即可
  - 多文件重构必须做全量验证，不可省略
```

### 反模式(必须避免)

```
❌ 修改完成后不验证，等用户反馈才发现错误
❌ 验证失败后开启全新的搜索+修改循环(而非在当前步骤内修正)
❌ 修改了A文件但忘记验证B文件(依赖文件)的编译状态
❌ 对单参数变更做完整compile+test验证(验证过度)
❌ 对多文件重构只做compile不做test(验证不足)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| undo操作 | 5次/2天 | 0-1次/2天 |
| 返工率 | 60% | <20% |
| 验证步骤冗余率 | ~40% | <10% |

## 策略三：搜索结果缓存

### 何时使用
多步骤任务中需要多次搜索同一代码区域时。

### 执行流程

```
Step 1: 第一次搜索 — 正常执行SearchCodebase/Grep/Read
Step 2: 在TodoWrite或回复中记录已搜索的关键发现
  - 记录: 哪些文件已读取、哪些代码位置已确认
  - 后续步骤可以复用这些发现

Step 3: 后续步骤 — 优先复用已获取的上下文
  - 如果已读取文件A的内容，不再重复Read文件A
  - 如果已SearchCodebase获取某模块的上下文，不再重复搜索
  - 除非文件被修改(由SearchReplace导致)，才需要重新Read

Step 4: 文件修改后 — 只重新读取被修改的文件
  - 用SearchReplace修改文件后，如果需要再次引用该文件内容
  - 才执行Read重新获取修改后的版本
```

### 大文件精准读取

对大文件(>500行)，不要整体Read浪费上下文窗口，应精准读取目标区域：

```
Step 1: 先用SearchCodebase获取文件中的关键代码片段
  - 搜索特定方法名/类名，获取带行号的片段
  - 从片段中定位目标代码的行号范围

Step 2: 用Read + offset/limit只读目标区域
  - 只读取确认需要的行范围(通常20-50行)
  - 而非读取整个文件

Step 3: 如果SearchCodebase返回的片段足够理解上下文
  - 可以跳过Read步骤，直接修改
  - 仅在需要精确行号做SearchReplace时才Read

文件大小阈值:
  - <200行: 可以整体Read
  - 200-500行: 优先SearchCodebase定位后Read片段
  - >500行: 必须先SearchCodebase定位，再offset/limit精准读取
```

### 反模式(必须避免)

```
❌ 在同一对话中多次Read同一文件(文件内容未变化时)
❌ 在同一对话中多次SearchCodebase同一查询
❌ 搜索得到结果后不记录，后续步骤又重新搜索同一内容
❌ 对>500行文件整体Read (浪费上下文窗口)
❌ 不先用SearchCodebase定位方法位置就盲目Read大文件
❌ Read了整个大文件但只用其中3-5行信息
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 重复搜索率 | ~30% | <10% |
| 平均工具调用数/任务 | 10次 | 5次 |
| 大文件上下文浪费率 | ~95% | <20% |

## 策略四：分层规划

### 何时使用
复杂任务(涉及3+文件修改、架构调整、新功能开发)开始前。

### 执行流程

```
Step 1: 理解层 — SearchCodebase获取代码架构和关键路径
  - 搜索项目整体结构
  - 搜索目标模块的依赖关系
  - 搜索相关的设计文档或README

Step 2: 规划层 — TodoWrite列出所有修改点
  - 列出每个需要修改的文件
  - 列出每个文件中的修改位置
  - 列出修改的顺序(考虑依赖关系)
  - 列出验证步骤

Step 3: 执行层 — 按规划顺序执行SearchReplace
  - 按TodoWrite的顺序逐个修改
  - 尽量把同一文件的多个修改合并为一次SearchReplace
  - 修改后标记TodoWrite对应项为completed

Step 4: 验证层 — RunCommand编译+测试
  - 执行编译确认所有修改无语法错误
  - 执行测试确认功能正确
  - 如有错误，在当前步骤内修正

Step 5: 修正层 — 仅在验证失败时进入
  - 分析错误信息
  - 针对错误精确修正(而非重新搜索)
  - 修正后再次验证
```

### 反模式(必须避免)

```
❌ 不规划直接开始修改(导致遗漏、返工)
❌ 修改了文件A后才发现还需要修改文件B(依赖发现不及时)
❌ 逐文件单独修改而非批量规划(同模块文件应一起修改)
```

### Java项目专用规划模板

```
TodoWrite规划模板:
1. [理解] SearchCodebase获取<模块>完整上下文
2. [理解] 确认所有需要修改的文件列表
3. [修改] <文件1>: <修改描述>
4. [修改] <文件2>: <修改描述>
5. [修改] <文件3>: <修改描述>
6. [验证] mvn compile 确认编译通过
7. [验证] mvn test -Dtest=<TestClass> 确认测试通过
```

## 策略五：智能工具选择

### 何时使用
每个搜索步骤开始时，选择最合适的搜索工具。

### 工具选择决策树

```
需要搜索代码 → 问题类型?
  ├─ "这段代码的作用是什么?" → SearchCodebase (语义理解)
  ├─ "哪里使用了XXX类/方法?" → SearchCodebase (依赖追踪)
  ├─ "XXX模式在哪些文件中出现?" → Grep (精确模式匹配)
  ├─ "项目中有哪些XXX类型的文件?" → Glob (文件发现)
  ├─ "我需要修改这个文件" → Read (仅在确认修改目标后)
  ├─ "这个错误是什么原因?" → SearchCodebase + Grep (先语义再精确)
  ├─ "这个模块的整体设计?" → SearchCodebase (架构级理解)
  └─ "大文件中的某个方法在哪?" → SearchCodebase定位 → Read+offset/limit (精准读取)
```

### 工具效率对比

| 工具 | 上下文获取量 | 调用成本 | 适用场景 |
|------|-------------|----------|----------|
| SearchCodebase | 高(跨文件语义片段) | 1次调用 | 理解意图、架构、依赖 |
| Grep | 中(精确匹配行) | 1次调用 | 定位特定类名/方法名/字符串 |
| Read | 高(完整文件) | 1次调用 | 仅在确认修改目标后 |
| Read+offset/limit | 低(精准片段) | 1次调用 | 大文件中只读目标区域 |
| Glob | 低(文件路径列表) | 1次调用 | 发现文件位置 |
| LS | 低(目录结构) | 1次调用 | 了解项目目录结构 |

### 反模式(必须避免)

```
❌ 用Read逐文件读取来理解项目(应先用SearchCodebase)
❌ 用Grep逐关键词搜索来拼凑上下文(应先用SearchCodebase获取语义上下文)
❌ 在不确定修改目标前就Read文件(浪费上下文窗口)
❌ 搜索到结果后不分析直接修改(应先理解再修改)
❌ 对大文件整体Read而非先SearchCodebase定位后精准Read(浪费上下文)
```

## 策略六：任务类型路由

### 何时使用
任何任务开始前，应首先判断任务类型，选择对应的最优执行路径。

### 任务类型分类与最优路径

```
类型A: Bug修复 → 测试先行→错误分析→精准搜索→最小修复→验证
  - 先运行失败测试获取错误信息
  - 从错误信息提取关键线索做精准搜索
  - 找参照模式(同类通过用例)指导修复
  - 只做最小必要修改
  - 用目标测试验证(跳过冗余compile)

类型B: 新功能开发 → 预搜索→规划→批量修改→编译→测试
  - 先用SearchCodebase理解相关模块
  - 规划所有需要新增/修改的文件
  - 批量完成所有修改
  - compile确认无语法错误
  - 测试确认功能正确

类型C: 重构 → 预搜索→影响分析→规划→批量修改→全量测试
  - 先用SearchCodebase理解重构范围和影响面
  - 列出所有受影响的文件
  - 批量完成所有修改
  - compile + 全量测试确认无破坏

类型D: 代码解释 → SearchCodebase→总结(无修改)
  - 用SearchCodebase获取代码上下文
  - 总结关键发现，不需要任何修改
  - 不需要验证步骤

类型E: 配置调整 → 定位配置→修改→验证
  - 用Glob/SearchCodebase定位配置文件
  - 修改配置
  - 用轻量验证确认配置生效
```

### 路由决策树

```
任务关键词 → 类型路由
  "修复/fix/bug/错误/失败/fail/error" → 类型A (Bug修复)
  "添加/新增/add/create/开发/develop" → 类型B (新功能)
  "重构/refactor/优化/optimize/重命名/rename" → 类型C (重构)
  "解释/explain/理解/understand/分析/analyze" → 类型D (代码解释)
  "修改配置/config/调整参数/parameter" → 类型E (配置调整)
```

### 反模式(必须避免)

```
❌ Bug修复走"预搜索→修改→验证"流程(应走"测试先行→错误驱动"流程)
❌ 不判断任务类型，所有任务走同一流程(效率低下)
❌ Bug修复时不先运行测试获取错误信息(盲目搜索根因)
❌ 简单配置调整走完整compile+test验证流程(验证过度)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| Bug修复平均工具调用 | ~15次 | ~8次 |
| 任务类型误路由率 | ~50% | <10% |
| 验证步骤冗余率 | ~40% | <10% |

## 策略七：错误驱动搜索

### 何时使用
测试或编译失败后，需要搜索根因和修复方案时。

### 执行流程

```
Step 1: 提取错误关键信息 — 从错误日志中精准提取:
  - 异常类型和异常消息
  - 失败的断言/期望值 vs 实际值
  - 关键类名/方法名/变量名
  - 堆栈中的关键调用路径
  - 相关的日志/输出信息

Step 2: 用提取的关键信息做精准SearchCodebase
  - 搜索异常类型 → 找到处理该异常的代码
  - 搜索断言相关的类 → 找到类似的成功模式
  - 搜索堆栈中的关键方法 → 找到根因代码
  - 搜索错误消息中的关键词 → 找到产生该错误的源头

Step 3: 仅对SearchCodebase返回的精准片段做Read
  - 只读取确认需要理解/修改的代码段
  - 大文件(>500行)用offset/limit只读目标区域
  - 避免读取整个文件来寻找一小段根因代码

Step 4: 原地修正而非重新搜索
  - 基于精准搜索结果直接修正
  - 修正后立即验证
  - 不要回到Step 1开启新的搜索循环
```

### 错误信息提取模板

```
从错误日志中提取以下信息用于精准搜索:
1. 异常全名: com.xxx.SomeException → SearchCodebase("SomeException 产生原因")
2. 断言失败: expected X but was Y → SearchCodebase("产生Y的代码路径")
3. 关键类名: SomeClass.someMethod → SearchCodebase("SomeClass someMethod 实现")
4. 错误消息关键词: "Failed to serialize" → SearchCodebase("serialize 失败处理方式")
5. 堆栈入口: topLevelMethod → SearchCodebase("topLevelMethod 调用链路")
```

### 反模式(必须避免)

```
❌ 测试失败后不分析错误日志，直接扩大搜索范围
❌ 用Read逐个读取"可能相关"的文件来找根因(应先用SearchCodebase精准搜索)
❌ 从错误日志中提取了关键信息但没有用它做精准搜索(浪费了错误信息的价值)
❌ 测试失败后开启全新的"预搜索→理解→修改"循环(应走错误驱动搜索路径)
❌ 忽略错误日志中的细节，只看表面错误消息(遗漏深层根因线索)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 失败后搜索步骤数 | 3-5次Read | 1-2次SearchCodebase |
| 错误信息利用率 | ~20% | >80% |
| Bug修复返工率 | ~40% | <15% |

## 策略八：参照模式发现

### 何时使用
修复失败测试/用例时，需要找到同类通过用例作为修复参考。

### 执行流程

```
Step 1: 定位失败用例所在目录
  - 从失败用例的文件路径中提取目录信息
  - 确认同目录下有哪些类似用例

Step 2: SearchCodebase搜索同目录下的类似通过用例
  - 搜索关键词: 同目录 + 同功能类型
  - 目标: 找到最相似的已通过用例作为参照
  - 优先选择: 与失败用例使用相同框架/组件/依赖的通过用例

Step 3: 对比失败用例与通过用例的差异
  - 检查: 配置方式、初始化方式、依赖注入、断言模式
  - 检查: 是否使用了不同的库/工具/参数
  - 找出: 通过用例用了什么失败用例没有的模式
  - 找出: 失败用例用了什么通过用例避免的模式

Step 4: 将通过用例的模式应用到失败用例
  - 原则: 优先采用已验证的模式，而非自行设计新方案
  - 只做最小必要修改，将失败模式替换为通过模式
  - 不要照搬整个文件，只移植关键差异部分
```

### 参照模式选择原则

```
选择参照用例的优先级:
1. 同目录 + 同功能类型 + 最近通过的 → 最佳参照
2. 同目录 + 相似功能类型 + 通过的 → 次佳参照
3. 不同目录 + 同功能类型 + 通过的 → 可用参照
4. 同目录 + 不同功能类型 → 不适合(差异过大)
```

### 反模式(必须避免)

```
❌ 不找参照模式，凭直觉自行设计修复方案(返工风险高)
❌ 找到参照后不对比差异，直接照搬整个文件(过度修改)
❌ 找多个参照但不选最相似的，导致修复方向偏离
❌ 选择与失败用例差异过大的参照(参照不相关)
❌ 只找1个参照就定方案，应找2-3个对比后选最合适的
```

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 参照模式发现步骤 | 3-5次Read | 1次SearchCodebase |
| 修复成功率(首次) | ~60% | >85% |
| 返工率(因方案错误) | ~30% | <10% |

## 策略九：并行工具调用

### 何时使用
多个独立搜索/读取/验证操作可以同时执行时。

### 并行调用规则

```
规则1: 多个独立搜索 → 同一消息中并行调用
  - 例: SearchCodebase查模块A + SearchCodebase查模块B (同时发起)
  - 例: Glob找文件A + Glob找文件B (同时发起)
  - 例: SearchCodebase语义搜索 + Grep精确搜索 (互补并行)

规则2: 多个独立Read → 同一消息中并行调用
  - 例: Read文件A + Read文件B (同时发起，如果两者都需要且互不依赖)

规则3: 修改后的独立验证 → 可以并行
  - 例: RunCommand compile + RunCommand git status (同时发起)

规则4: 修改前的多维度搜索 → 同一消息中并行调用
  - 例: SearchCodebase理解意图 + Grep定位方法 + Glob发现文件 (三维并行)

不可并行的情况:
  - 修改依赖搜索结果 → 先搜索再修改 (串行)
  - 验证依赖修改结果 → 先修改再验证 (串行)
  - 第二次搜索依赖第一次的结果 → 串行
  - 对同一文件同时Read和SearchReplace → 先Read再修改 (串行)
```

### 并行调用示例

```
并行场景1: 初始理解阶段
  同时发起: SearchCodebase("模块架构") + Grep("关键类名") + Glob("相关文件类型")
  → 一次性获取架构理解+精确定位+文件发现

并行场景2: 错误分析阶段
  同时发起: SearchCodebase("异常类型根因") + SearchCodebase("同类通过用例")
  → 同时获取根因线索和参照模式

并行场景3: 修改前准备阶段
  同时发起: Read文件A + Read文件B + Read文件C (如果三者互不依赖)
  → 一次性获取所有需要修改的文件内容

并行场景4: 验证阶段
  同时发起: RunCommand compile + RunCommand git status
  → 同时验证编译状态和工作区状态
```

### 反模式(必须避免)

```
❌ 多个独立搜索逐个串行执行(应并行发起)
❌ 多个独立文件Read逐个串行执行(应并行发起)
❌ 编译验证和git status串行执行(应并行发起)
❌ 对同一文件同时Read和修改(应先Read再修改)
❌ 后一步依赖前一步结果但仍强行并行(逻辑错误)
```

### 目标指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 并行执行率 | ~0% | ~30% |
| 平均对话往返次数 | ~10轮 | ~6轮 |
| 任务总耗时 | 2-5分钟 | 1-2分钟 |

## 系统性问题修复建议

以下问题不是Skill能解决的，但执行任务时应注意规避：

### 沙箱崩溃(Sandbox Crash)

- 现象: RunCommand可能因沙箱崩溃而丢失结果
- 规避: 如果RunCommand返回异常(空结果/错误)，等待2-3秒后重新执行
- 根因修复: 需要升级TRAE CN的sbox SDK版本或修复路径配置

### Job持久化失败

- 现象: Task子Agent状态可能丢失
- 规避: 避免依赖Task工具的长时运行结果，尽量在主对话中完成所有步骤
- 根因修复: 需要修复8.3短路径名问题(YAODON~1 → yaodonghai)

### LLM响应延迟

- 现象: 首Token最大可达14.6秒
- 规避: 简单任务(单文件修改/代码解释)建议使用Doubao-Seed-Code快速模型
- 复杂任务(多文件重构/架构设计)使用GLM-5.1或更强模型

□ 11. Bug修复是否先运行测试获取错误信息? (而非盲目预搜索)
