# Code Wiki Author — 代码仓库文档化技能

> 本技能提炼自一次完整的 agent-core(3463 行核心文件 / 20+ 子模块)文档化实战,并融合业界 Diátaxis 框架与「Docs as Code」实践,形成可复用的代码仓库文档化方法论。

## 一、何时调用

- 用户要求"分析并理解某项目仓库"
- 用户要求"生成项目文档 / Code Wiki / 架构文档"
- 用户要求"解读仓库结构 / 模块职责 / 关键类函数"
- 用户要求"为代码写说明文档,输出到指定目录"
- 需要为已有代码库建立可持续维护的文档体系

---

## 二、核心方法论:五阶段流水线

### 阶段 1 — 意图澄清(写文档前必做)

复杂文档任务前,**用 AskUserQuestion 提 5 个以上问题**,全部为「是否」或「选择」题(禁止自由作答)。批量提问(每次最多 4 个,分批凑齐)。

必问维度:
1. **覆盖范围**:文档要覆盖哪些场景(全场景 / 仅某几类)
2. **分析深度**:仅能力概览 / 能力清单+入口 / 深入源码实现(类/函数/调用链)
3. **文档组织**:单个综合文档 / 按模块拆分 / 按能力维度拆分
4. **命名风格**:序号前缀(中文)/ 序号前缀(英文)/ 纯英文短名 / 中文能力名
5. **内容元素**:是否含调用示例、交叉引用、业界对比、代码片段
6. **导航策略**:主 README 是否汇总索引、是否分特性子目录

> 提问能避免 5.2:1 的搜索返工率(见 efficient-task-flow 技能),意图不清就动手是文档返工的首因。

### 阶段 2 — 自顶向下读码(理解优先于记录)

**读码顺序(从外到内、从粗到细):**

```
1. README.md / docs/          ← 项目定位、快速开始、官方架构说明
2. pyproject.toml / package.json / Cargo.toml  ← 依赖、入口点、可选依赖组
3. AGENTS.md / CLAUDE.md / CONTRIBUTING.md  ← 贡献者约定、模块职责、架构规则
4. .claude/rules/architecture.md / 架构决策记录  ← 显式架构约束
5. <package>/__init__.py 各层  ← 懒加载导出模式(看 __all__ 与 __getattr__)
6. 关键大文件全文精读         ← 核心类、设计模式、数据流(如 deep_agent.py 3463 行)
7. 子模块逐层下沉             ← 子目录 __init__.py + 关键实现文件
```

**读码原则:**
- **先广后深**:先 LS/Glob 看全貌,再 Read 关键文件,最后全文精读核心
- **Card/Config 分离**:识别"静态可序列化元数据(Card)"与"运行时对象(Config)"的设计模式
- **找单例与入口**:进程级单例(Runner/Manager)、工厂函数(create_xxx)是理解架构的钥匙
- **追事件钩子**:before/after_xxx_call 的回调注册点揭示扩展机制

**并行加速:** 大仓库(>10 子模块)派发 4 个搜索子代理,每个聚焦一个模块簇,返回结构化分析(类名/函数名/文件绝对路径+行号/调用链)。子代理 prompt 必须要求 `file:///绝对路径#L行号` 格式定位。

### 阶段 3 — 结构设计(先骨架后血肉)

**主文档集(00-09 编号序列,便于排序与有序阅读):**

| 序号 | 文档类型 | 内容 |
|------|---------|------|
| 00 | 路标与增量更新说明 | 任务时间线、git 基线提交、产物清单、后续增量更新流程 |
| 01 | 项目概述 | 定位、核心能力、特性、技术栈、仓库结构 |
| 02 | 整体架构 | 分层架构、核心设计模式(10 大)、运行时数据流、关键概念 |
| 03-N | 逐模块文档 | 每个顶层模块一篇,含子模块职责、关键类、设计模式 |
| N+1 | 依赖关系 | 内部依赖图、外部依赖表、可选依赖组、入口点 |
| N+2 | 运行方式 | 安装、配置、CLI 入口、编程式使用、测试、代码质量 |

**业界补充 — Diátaxis 四象限(可选叠加):**
主文档集偏「Reference + Explanation」,若仓库面向外部用户,可叠加:
- Tutorials(学习导向,面向新手,不解决具体问题)
- How-to guides(任务导向,解决具体问题)
- Reference(信息导向,描述机制,严谨干燥)
- Explanation(理解导向,澄清、讨论、权衡)

> Cloudflare / Gatsby / Django / Vue 均采用 Diátaxis。内部文档可只取 Reference+Explanation 两象限。

**特性子目录(features/<domain>/):**
按能力维度拆分,每篇聚焦一个特性,英文短名命名。子目录自带 README 作能力判定 + 文档索引 + 关键入口。

### 阶段 4 — 并行写作(模板统一 + 批量子代理)

**统一文档模板(每篇能力文档都按此结构,保证可读性与可比性):**

```markdown
# {能力中文名}

> 交叉引用: [01-项目概述](../01-project-overview.md) | [02-整体架构](../02-overall-architecture.md) | [04-某模块](../04-xxx.md) | [08-依赖关系](../08-dependencies.md)

## 一、能力概述
{2-3 段:定义、价值、在项目中的定位}

## 二、关键类与函数
{Markdown 表格: 类/函数 | 文件位置 | 说明}
{每行用 [文件名](file:///绝对路径#L行号) 格式,链接文本用 basename/类名,不加反引号}

## 三、实现机制
{调用链/数据流/关键设计,含代码片段或文字时序}

## 四、调用示例
{真实 API 调用的 Python 代码块}

## 五、业界对比
{表格: 能力维度 | 本项目 | 竞品A | 竞品B | 竞品C}

## 六、小结
{3-5 条要点}
```

**并行写作:** 12 篇文档派发 3 个写作子代理(每批 4 篇),每个子代理获得:①要创建的文件绝对路径 ②统一模板 ③对应源码分析素材(含类名/行号/调用链) ④写作要求(章节齐全、链接格式、行数区间)。子代理用 Write 工具创建文件并返回清单+行数。

### 阶段 5 — 增量更新与版本同步(可持续维护)

**路标文档(00)核心字段:**
- 基线提交: `git rev-parse HEAD` 完整哈希 + `git describe --tags --always` + 分支状态 + 时间戳
- 产物清单: 全部文档文件路径 + 行数
- 增量更新流程: `git log <基线>..HEAD` 取增量 → 按提交→文档映射表分析 diff → 更新对应文档 → 追加更新记录
- 提交→文档映射表(基于 conventional commit 前缀 + 文件路径):
  | 提交特征 | 影响路径 | 目标文档 |
  |---------|---------|---------|
  | `feat(core)` / 路径含 `core/` | `core/**` | `03-core-module.md` |
  | 依赖变更 | `pyproject.toml` | `08-dependencies.md` |
  | ... | ... | ... |
- 更新检查清单(8 项):确认基线、取增量、分类、更新文档、追加记录、验证链接、提交、推送

## 三、写作技巧(实战提炼)

### 3.1 可导航性优先
- **代码行号锚点**:所有类/函数引用用 `[basename](file:///绝对路径#L行号)`,可点击直达源码行
- **交叉引用头部**:每篇文档顶部固定一行 `> 交叉引用: [01] | [02] | ...`,形成知识网络
- **README 索引表**:主 README 用表格汇总全部文档(序号 | 文档 | 内容简介)
- **特性子目录 README**:主 README 只给特性列表+说明+导航到子 README,不展开细节

### 3.2 可读性结构
- **表格化**:类/函数清单、能力清单、依赖表、对比表全部用 Markdown 表格
- **加粗强调**:关键设计模式、核心概念用 **加粗**
- **代码块**:调用示例、配置、命令用带语言标签的代码块
- **行数控制**:能力文档 150-300 行/篇,索引文档 80-150 行,主文档 200-500 行
- **避冗余**:同一信息只在一处详述,他处交叉引用

### 3.3 准确性保障
- **源码核验**:写作前逐一核验关键源码行号(子代理 prompt 要求返回行号,写手再抽检)
- **断链检测**:完成后 `grep` 检查 `[中文字符]\.md` 残留、`file:///` 链接有效性
- **结构验证**:grep `## ` 章节标题,确认 6 章节齐全;grep `交叉引用|业界对比` 确认关键节存在

### 3.4 命名一致性
- **英文短名**:特性文档用英文短名(code-editing.md / code-navigation.md),便于排序与跨平台
- **序号前缀**:主文档集保留 `00-`~`09-` 序号前缀,兼顾排序与可读
- **重命名一致性**:改文件名时同步更新所有交叉引用(可用脚本批量替换,UTF-8 无 BOM 写回)

## 四、业界实践补充(选读采纳)

### 4.1 Docs as Code
- 文档用 Markdown,纳入 git 版本控制,与代码同仓库同提交
- PR review 同时审代码与文档
- CI 校验链接有效性、拼写、格式

### 4.2 Diátaxis 四象限(面向外部用户时叠加)
- Tutorials:学习导向,面向新手,手把手,不解释为什么
- How-to guides:任务导向,解决具体问题,可跳过
- Reference:信息导向,严谨干燥,无解释,按 API 组织
- Explanation:理解导向,讨论背景、权衡、历史

### 4.3 ADR(架构决策记录)
重大架构决策单独记录:Context(背景)→ Decision(决策)→ Status(状态)→ Consequences(后果)。可放在 `docs/adr/` 目录。

### 4.4 写作心法
- **写给读者,不是写给作者**:假设读者不知道你脑子里的上下文
- **先 skim 友好**:标题、表格、列表让快速浏览者 30 秒抓重点
- **示例可运行**:代码示例必须能复制粘贴运行,避免伪代码
- **保持同步**:文档与代码同生命周期,过期文档比没有文档更危险

## 五、执行规则(强制)

1. **意图不清不动手**:复杂任务先提 5+ 个选择/是否题,确认后再执行
2. **语言一致**:文档语言与用户最新消息语言一致(用户中文则文档中文,除非用户指定英文)
3. **不擅自提交**:生成文档后不主动 git commit,除非用户明确要求
4. **不擅自创建**:优先编辑现有文件,不创建非必要文件,不主动建 README/文档除非要求
5. **任务追踪**:多步骤任务用 TodoWrite 实时追踪,完成即标记
6. **验证后宣称**:完成前用 grep/ls 验证结构、链接、章节,证据先于断言

## 七、适用与边界

**适用:**
- 中大型代码仓库(>5 子模块,>5000 行)的文档化
- 需要可持续维护(增量更新)的项目文档
- 需要特性维度深入分析的能力文档

**不适用:**
- 单文件/小脚本(直接注释即可,无需 Wiki)
- 一次性快速 README(用通用写作即可)
- 用户手册/产品文档(用 Diátaxis Tutorials/How-to 而非本技能)
