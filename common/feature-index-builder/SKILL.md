# Feature Index Builder — 特性索引构建与演进技能

> 本技能是 `feature-analysis` 的配套细化技能：`feature-analysis` 负责「理解+定位」全流程，本技能聚焦其中的「产出特性索引」这一交付物，把索引的结构、构建、质量校验、增量演进标准化。二者可串联：先 `feature-analysis` 分析，再用本技能沉淀索引。

---

## 一、何时调用

- 用户要求「建特性清单 / 特性索引 / 功能清单 / feature index」
- 用户要求「梳理这个项目有哪些功能」并产出结构化可导航清单
- 既有索引需要「增量更新」(代码改动后追加/更新行)
- 既有索引需要「漂移校验」(实际代码与索引是否一致)
- 接手工程后要建立团队共享、可持续维护的功能基线

**不适用：** 只要口头理解不要产出(走 `feature-analysis`)；要成完整文档体系(走 `code-wiki-author`)；纯改代码(走 `efficient-task-flow`)。

---

## 二、索引产物结构

一次完整构建产出 3 类文件：

| 产物 | 路径 | 作用 |
|------|------|------|
| 特性索引表 | `docs/feature-index.md` | 核心交付，一行一特性 |
| ADR 集合 | `docs/adr/NNNN-title.md` | 关键特性的决策记录 |
| 索引基线 | `docs/feature-index-baseline.md` | 基线提交、更新流程、提交→特性映射表、更新记录 |

> 路径可按团队约定调整，但三件套应同目录共存，便于交叉引用。

---

## 三、索引表 Schema

### 3.1 主表 `feature-index.md` 字段

| 列 | 说明 | 示例 |
|----|------|------|
| 特性名 | 中文短名，团队惯用 | 用户登录 |
| 职责 | 一句话说明做什么 | 校验账密并签发 token |
| 入口 | 路由/CLI/事件触发点 | `[AuthController](file:///abs/path#L42)` |
| 实现 | 核心实现位置 | `[loginService](file:///abs/path#L88)` |
| 测试 | 对应测试位置 | `[AuthTest](file:///abs/path#L12)` |
| 依赖 | 上下游特性/模块 | ←用户模块, →Token服务 |
| ADR | 决策记录链接 | `[ADR-0003](./adr/0003-login-flow.md)` |
| 状态 | active/deprecated/experimental | active |

### 3.2 链接格式约定（强制）
- 代码/测试位置一律 `[basename](file:///绝对路径#L行号)`，可点击直达源码行
- 链接文本用 basename/类名/函数名，**不加反引号**（会破坏链接渲染）
- ADR 用相对路径 `./adr/NNNN-title.md`
- 跨文档引用统一相对路径

### 3.3 排序与分组
- 按「特性域」分组（用 `## 域名` 二级标题），域内按特性名排序
- 顶部固定一行交叉引用：`> 交叉引用: [基线](./feature-index-baseline.md) | [ADR目录](./adr/)`
- 主表前附「特性域概览表」(域 | 特性数 | 关键入口)

## 四、构建流程（标准 6 步）

```
Step 1: 基线锁定
  - RunCommand: git rev-parse HEAD → 完整哈希
  - RunCommand: git describe --tags --always → tag
  - RunCommand: git status -sb → 分支状态
  - 记录到 feature-index-baseline.md

Step 2: 特性发现（多来源并查，避免漏特性）
  - 来源见「五、特性发现来源」
  - 用并发子代理(Task)分模块回传「特性候选清单」
  - 去重、合并、命名归一

Step 3: 可追踪性矩阵构建（见「六」）
  - 每个特性定位：入口→实现→测试→依赖
  - 三路定位：静态(Grep/ast-grep)+文本(SearchCodebase)+动态(跑测试)
  - 记录 file:///绝对路径#L行号

Step 4: ADR 撰写（关键特性才写，见「七」）
  - 不是每个特性都写 ADR，只写有架构权衡的
  - 命名 docs/adr/NNNN-kebab-title.md

Step 5: 主表与基线文件落盘
  - Write feature-index.md（主表+域概览+交叉引用）
  - Write feature-index-baseline.md（基线+映射表+更新流程+更新记录）
  - 按 ADR 模板 Write 各 ADR

Step 6: 质量校验（见「九」）
  - grep 断链、grep 章节、抽样核验行号、build/test 交叉验证
```

---

## 五、特性发现来源（多来源并查）

单一来源必漏，必须从以下来源交叉汇总：

| 来源 | 提取方式 | 揭示什么 |
|------|---------|---------|
| 路由/API 表 | Grep 路由注解/配置 | 对外暴露的功能 |
| CLI 命令 | 读 main/argparse/click | 命令行功能 |
| 事件/钩子注册 | Grep before/after/hook | 扩展点功能 |
| 测试用例 | Glob `*Test`/`test_*` 读名字 | 已验证行为契约 |
| 配置/feature flag | 读 config/yaml | 可开关功能 |
| 顶层模块目录 | LS + 读各 `__init__`/`package-info` | 功能域划分 |
| README/docs | Read | 官方宣称的功能 |
| git log | `git log --oneline` 看 `feat:` 提交 | 已交付功能演化 |
| 菜单/权限表 | Grep 权限码/菜单项 | 业务功能点 |

> 并发策略：大工程(>10 模块)派 4 个子代理，每个聚焦一组来源，回传结构化候选(特性名|候选入口|候选测试|来源)。

## 六、可追踪性矩阵构建

### 6.1 三向映射
```
特性 ←→ 代码(入口+实现) ←→ 测试
```
- 入口：触发该特性的最外层(路由/CLI/事件)
- 实现：核心逻辑所在(类/函数)
- 测试：覆盖该特性的测试用例
- 依赖：该特性调用/被调用的其它特性或外部模块

### 6.2 定位精度要求
- 行号必须实测，不可臆造：定位后用 Read 抽检该行确属所述代码
- 实现/测试位置给到「最小充分」范围：函数级用 `#L起始`，跨多行用 `#L起始-L结束`
- 一个特性可有多入口/多实现/多测试，用 `<br>` 分行或子表

### 6.3 三路定位法（与 feature-analysis 一致）
```
文本法(SearchCodebase) 定种子 → 静态法(Grep/ast-grep) 扩依赖 → 动态法(跑测试/抓栈) 验行为
```
三路结论一致才入表；不一致标 `状态=待核` 并记疑点。

## 七、ADR 写作规范

### 7.1 模板
```markdown
# ADR-NNNN: <决策标题>

- 状态：proposed | accepted | deprecated | superseded by [ADR-XXXX]
- 日期：YYYY-MM-DD
- 关联特性：[特性名](../feature-index.md)

## 背景（Context）
为什么要做这个决策？触发因素、约束、问题

## 决策（Decision）
我们决定……

## 后果（Consequences）
正面：……
负面：……
中性：……

## 替代方案（Alternatives）
考虑过但否决的方案及原因
```

### 7.2 写与不写
- **写**：有架构权衡、有多种可行方案、影响多个特性、涉及技术选型
- **不写**：纯 CRUD、命名习惯、无争议实现细节
- 原则：ADR 贵精不贵多，宁缺毋滥

## 八、增量更新与漂移校验

### 8.1 基线文件核心字段
```markdown
# 特性索引基线

- 基线提交：<完整哈希>
- tag：<git describe>
- 分支状态：<git status -sb>
- 构建时间：<时间戳>

## 提交→特性映射表（基于 conventional commit + 路径）
| 提交特征 | 影响路径 | 目标特性行 |
|---------|---------|-----------|
| feat(auth) / 路径含 auth/ | auth/** | 用户登录、鉴权 |
| feat(core) / 路径含 core/ | core/** | 核心调度 |
| 依赖变更 | pom.xml/package.json | （记更新记录） |
| ... | ... | ... |

## 增量更新流程
1. git log <基线>..HEAD 取增量提交
2. 按映射表分析 diff 影响哪些特性
3. 更新对应特性行(入口/实现/测试行号、状态)
4. 新增特性追加新行 + 新域则加分组
5. 追加更新记录
6. 更新基线提交为当前 HEAD
7. 质量校验（九）

## 更新记录
| 日期 | 提交 | 变更特性 | 操作 |
|------|------|---------|------|
| ... | ... | ... | 新增/更新/废弃 |
```

### 8.2 漂移校验（用 Schedule 定期跑）
- 定期重跑特性发现，对比新候选 vs 现有索引行
- 对每个特性行：重新 Grep 入口/实现/测试，行号是否仍有效
- 失效行号 → 标 `状态=漂移`，记入更新记录
- 新增未被索引的特性 → 标 `状态=待补`
- 建议频率：每周或每个迭代末

### 8.3 反模式（必须避免）
```
❌ 行号臆造不核验（断链）
❌ 单一来源发现特性（必漏）
❌ 索引建完不锁基线（无法增量）
❌ 改代码不更新索引（索引漂移失效）
❌ 每个特性都写 ADR（噪声淹没信号）
❌ 链接文本加反引号（破坏渲染）
```

## 九、质量检查清单（交付前必过）

- [ ] 主表含全部字段(特性名/职责/入口/实现/测试/依赖/ADR/状态)
- [ ] 所有代码/测试位置为 `[basename](file:///绝对路径#L行号)` 格式
- [ ] 链接文本未加反引号
- [ ] 顶部含交叉引用行
- [ ] 按特性域分组，域前有二级标题
- [ ] 基线文件含完整哈希、tag、分支状态、时间戳
- [ ] 基线文件含提交→特性映射表 + 增量更新流程 + 更新记录表
- [ ] 关键特性附 ADR（背景/决策/状态/后果/替代方案）
- [ ] ADR 命名 `NNNN-kebab-title.md`，状态字段正确
- [ ] grep `\[.*\]\(\.\./.*\)` 验证内部链接无断链
- [ ] grep `## ` 确认分组结构齐全
- [ ] 抽样核验：随机 3 个特性的入口/实现/测试行号实测有效
- [ ] 三路定位结论一致(不一致的已标 `状态=待核`)

---

## 十、执行规则（强制）

1. **基线先行**：构建前先锁基线提交，否则无法增量
2. **多来源并查**：特性发现至少用 3 个来源交叉，不可单一
3. **行号实测**：所有行号定位后用 Read 抽检，不臆造
4. **三路一致**：入口/实现/测试三路定位结论一致才入表
5. **链接规范**：`[basename](file:///绝对路径#L行号)`，文本不加反引号
6. **ADR 贵精**：只写有权衡的决策，不写实现细节
7. **语言一致**：输出语言与用户最新消息语言一致
8. **不擅自提交**：不主动 git commit，除非用户明确要求
9. **任务追踪**：多步骤用 TodoWrite 实时追踪，完成即标记
10. **演进闭环**：构建即锁基线，后续改动即增量更新+漂移校验

---

## 十一、适用与边界

**适用：**
- 中大型工程(>5 模块，>5000 行)建立特性基线
- 团队共享、可持续演进的功能清单
- 接手工程后的摸底交付物
- 重构/加功能前的依赖与影响分析底座

**不适用：**
- 单文件/小脚本(无需索引)
- 一次性口头理解(走 `feature-analysis`)
- 完整文档体系(走 `code-wiki-author`)

**串联建议：**
`feature-analysis`(理解+定位) → **`feature-index-builder`**(沉淀索引) → `code-wiki-author`(成文档) → `efficient-task-flow`(改代码时回写索引) 形成完整闭环。改代码后用本技能做增量更新，保证索引不漂移。
