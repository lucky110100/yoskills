# 可观测性 — 维度分析卡

> 维度归属：C 运行时质量组。评估日志、指标、追踪三大支柱与告警/错误聚合。区分：可靠性管"会不会挂"，本维度管"挂了能不能查清"。

## 评估信号（发现即记）

- 无结构化日志或无日志级别区分
- 无指标（metrics）采集
- 无分布式追踪（trace）
- 日志无关联 ID/traceId（无法串起一次请求）
- 无告警规则或告警噪声大
- 无错误聚合（无 Sentry/类似工具）
- 无健康检查端点

## 评估工具与命令

| 工具 | 命令/用法 | 看什么 |
|------|----------|--------|
| Grep | 查日志框架/指标库/追踪库引用 | 是否接入可观测设施 |
| Glob | 查配置（prometheus.yml/otel/loki） | 配置存在性 |
| RunCommand | `curl /health`/`/metrics` | 健康检查与指标端点 |
| Grep | 查 `traceId`/`requestId`/`correlationId` | 日志是否关联 |
| LS | 查监控/告警配置目录 | 告警规则完备度 |

## 评分锚点（5 档判定）

| 分 | 锚点信号 |
|----|---------|
| 4 | 日志结构化+级别分明+关联ID + 指标完整(RED/USE) + 分布式追踪 + 告警规则 + 错误聚合 + 健康检查 |
| 3 | 结构化日志 + 部分指标(RED 部分) + 无追踪 + 有健康检查 |
| 2 | 有日志但非结构化 + 无指标/追踪 + 无告警 |
| 1 | 日志零散 println 式 + 无任何监控设施 |
| 0 | 无任何可观测手段，故障黑盒 |

## 规范基线（新项目应做/不做）

- ✅ 应：结构化日志 + 关联 ID + RED 指标 + 分布式追踪(OpenTelemetry) + 告警规则 + 错误聚合 + 健康检查端点
- ❌ 不做：print 式日志 + 无关联 ID + 只看日志不看指标 + 无告警或告警全量广播

## 对标要点（业界标杆看哪些）

- 看标杆项目的可观测技术栈（OpenTelemetry/Prometheus/Loki/Sentry）
- 看其指标命名规范与 RED/USE 指标集
- 看其告警规则与 runbook 配套

## 反模式

```
❌ 日志 println 不结构化（无法聚合分析）
❌ 无 traceId（分布式下无法串请求）
❌ 只看日志无指标（看不出趋势与容量）
❌ 告警全量广播（噪声淹没真实问题）
```

## Checklist

- [ ] 日志是否结构化 + 级别分明
- [ ] 是否有关联 ID/traceId
- [ ] 是否采集 RED/USE 指标
- [ ] 是否接入分布式追踪
- [ ] 是否有告警规则与错误聚合
- [ ] 是否有健康检查端点
