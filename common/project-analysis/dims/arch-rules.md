# 架构约束/规则 — 维度分析卡

> 维度归属：B 代码质量组。评估分层规则、依赖方向、循环依赖、职责划分。与"代码规范"区分：本维度管"类/模块该不该依赖谁"，前者管"代码怎么写才好看"。

## 评估信号（发现即记）

- 跨层调用（Controller 直接调 DAO / Service 调 Controller）
- 循环依赖（A 依赖 B，B 依赖 A）
- 领域层依赖框架细节（领域对象耦合 Spring/MyBatis 注解）
- 上帝类/上帝包（一个类/包职责过多）
- 无分层或分层混乱（目录看不出职责边界）

## 评估工具与命令

| 工具 | 命令/用法 | 看什么 |
|------|----------|--------|
| ArchUnit(Java) | 架构规则测试 | 断言"Service 不调 Controller"等 |
| dependency-cruiser/madge(JS) | 依赖图 | 循环依赖、孤立模块 |
| import-linter(Python) | 导入规则 | 禁止跨层 import |
| ast-grep | 跨层调用模式 | Controller→DAO 直连等 |
| Grep | import/依赖方向 | 上层是否依赖下层细节 |
| LS + Glob | 目录骨架 | 分层是否清晰可读 |

## 评分锚点（5 档判定）

| 分 | 锚点信号 |
|----|---------|
| 4 | 有架构约束测试(ArchUnit 等) + 零循环依赖 + 依赖方向严格(领域不耦合框架) + 分层清晰 + 无上帝类 |
| 3 | 分层清晰 + 无循环依赖 + 无架构约束测试 + 偶有领域耦合框架 |
| 2 | 基本分层 + 偶有跨层调用 + 个别上帝类 |
| 1 | 分层混乱 + 多处跨层 + 部分循环依赖 |
| 0 | 无分层 / 循环依赖严重 / 多个上帝类 |

## 规范基线（新项目应做/不做）

- ✅ 应：明确定义分层与依赖方向 + 用 ArchUnit/import-linter 写架构测试 + 领域层隔离框架 + 目录反映职责边界
- ❌ 不做：领域对象耦合框架注解 + 循环依赖 + 上帝类包揽多职责 + 跨层直调

## 对标要点（业界标杆看哪些）

- 看标杆项目的分层架构文档与架构约束测试
- 看其 ArchUnit/import-linter 规则文件的严格度
- 对比目录结构是否清晰反映职责（如 DDD 分层、Clean Architecture）

## 反模式

```
❌ 有分层但无约束测试（演化后必然腐化）
❌ 领域层满框架注解（无法脱离框架复用）
❌ 循环依赖靠"以后再解"拖延
❌ 上帝类不改，新功能继续往里塞
```

## Checklist

- [ ] 是否有架构约束测试（ArchUnit/import-linter）
- [ ] 是否扫了循环依赖
- [ ] 是否查了跨层调用模式
- [ ] 领域层是否耦合框架
- [ ] 目录结构是否清晰反映分层
