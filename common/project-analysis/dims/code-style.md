# 代码规范 — 维度分析卡

> 维度归属：B 代码质量组。评估命名/格式/复杂度/注释的统一性与自动化程度。

## 评估信号（发现即记）

- 无统一格式化工具配置（搜不到 `.editorconfig`/`prettier`/`checkstyle`/`gofmt` 配置）
- 命名风格混用（驼峰与下划线交错、同一概念多译）
- 文件/函数过长（>500 行文件、圈复杂度 >15 函数）
- 魔法数字/硬编码字符串散布
- 注释缺失或陈旧（与代码不符）

## 评估工具与命令

| 工具 | 命令/用法 | 看什么 |
|------|----------|--------|
| Grep | 查格式工具配置文件名 | 有无自动化格式配置 |
| ast-grep | 按命名模式扫 | 命名是否一致 |
| RunCommand | 跑 lint（eslint/checkstyle/golangci-lint/ruff） | lint 报错数与类型 |
| radon/lizard/gocyclo | 复杂度扫描 | 高复杂度热点函数 |
| Glob | 查 `.editorconfig`/`.prettierrc`/`checkstyle.xml` | 配置存在性 |

## 评分锚点（5 档判定，不靠主观）

| 分 | 锚点信号 |
|----|---------|
| 4 | 有自动化格式工具 + lint 门禁(提交即拦) + 命名全局一致 + 无魔法数(常量集中) + 注释覆盖关键决策 |
| 3 | 有格式工具 + lint(无门禁) + 命名基本一致 + 偶有魔法数 |
| 2 | 有格式工具但常被绕过 + 命名部分不一致 + 存在长函数 |
| 1 | 无格式工具 + 命名混乱 + 大量魔法数 + 注释陈旧 |
| 0 | 无任何规范工具，风格完全随意 |

## 规范基线（新项目应做/不做）

- ✅ 应：配置 `.editorconfig` + 项目格式工具 + 提交前 lint hook + 常量集中管理 + 关键决策加注释
- ❌ 不做：依赖人工保持风格、魔法数散落代码、注释只写"what"不写"why"

## 对标要点（业界标杆看哪些）

- 看标杆项目的格式/lint 配置文件与 CI 门禁设置
- 看其 `.editorconfig` / `checkstyle.xml` / `.prettierrc` 的严格度
- 对比命名约定文档（CONTRIBUTING.md / STYLE.md）

## 反模式

```
❌ 靠人肉 review 保持风格（不可持续）
❌ 有 lint 但 CI 不拦（形同虚设）
❌ 复杂度热点不重构，长期累积成债
❌ 注释只描述代码做什么，不记为什么
```

## Checklist

- [ ] 是否有格式工具配置（`.editorconfig` 等）
- [ ] lint 是否接入 CI 门禁
- [ ] 是否扫了复杂度热点
- [ ] 抽样核验命名一致性
- [ ] 是否查了魔法数/硬编码
